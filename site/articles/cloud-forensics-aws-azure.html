Cloud Forensics: Investigating Incidents in AWS, Azure, and Google Cloud

File No.IGRS-037/2026
SubjectPractical guide to cloud forensic investigation — log sources, preservation, and legal process
CategoryDigital Forensics
AuthorManuj Kumar Pandey
Published2026-06-08
Reading time7 minutes

More Indian organizations are hosting critical systems in the cloud. When incidents occur there, traditional forensic approaches do not work. What does.

Why cloud forensics is different

Traditional digital forensics assumes physical access to storage media — imaging a hard drive, extracting data from a phone. Cloud environments invert these assumptions. The infrastructure is not yours to image, the storage is virtualized and distributed, and evidence that seems permanent may be deleted within hours by automated lifecycle policies. Cloud forensics requires different tools, different legal process, and a fundamentally different approach to evidence preservation — one that must begin immediately after an incident is detected, not after a measured forensic plan is developed.

Log sources by platform

AWS: CloudTrail is the primary investigation source — it logs every API call made to AWS services, with the calling identity, source IP, timestamp, and full request parameters. CloudTrail must be enabled; check immediately whether it was enabled and whether logging was disabled by the attacker during the incident. VPC Flow Logs capture network traffic metadata. S3 access logs show who accessed what objects and when. AWS Config snapshots resource configuration state at regular intervals, allowing reconstruction of what was configured at the time of an incident.

Azure: Azure Activity Log captures control-plane operations (creating/deleting resources, changing configurations). Azure AD Sign-in Logs show every authentication event with source IP, device, and outcome. Microsoft Defender for Cloud generates security alerts. Key Vault audit logs show who accessed secrets. NSG Flow Logs for network activity.

Google Cloud: Cloud Audit Logs (Admin Activity and Data Access logs) are the primary sources. VPC Flow Logs for network. Cloud Armor logs for WAF events.

Evidence preservation — the race against lifecycle policies

Cloud resources are often configured with automatic deletion policies that destroy logs and temporary storage. The first action in any cloud incident is to disable automatic deletion of logs for the affected environment, take snapshots of affected instances before they are terminated or rebuilt, and preserve any ephemeral storage (instance storage, in-memory data if accessible) before it is lost. Many cloud incidents are complicated by the fact that security teams discover them hours or days after they occurred — by which time some evidence may already have been destroyed by normal lifecycle operations.

Document your preservation actions with timestamps. Cloud forensics increasingly involves legal proceedings where defence counsel challenges the completeness and authenticity of evidence. A documented preservation chain — who did what, when, with what result — is your protection against these challenges.

Legal process for cloud providers

When an incident involves data stored or processed by a cloud provider, obtaining evidence beyond what is accessible through the organization's own console requires legal process. AWS, Azure, and GCP all maintain law enforcement response teams and respond to court orders and government legal process. For Indian law enforcement, this typically requires an international rogatory process unless the cloud region is India-based (AWS ap-south-1, Azure India Central). For Indian organizations investigating their own cloud environments, the organization's existing access rights allow evidence collection without third-party process — the question is which logs were retained and for how long.
