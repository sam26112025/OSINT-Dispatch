Supply Chain Attacks: How Investigators and Defenders Identify Compromised Software

File No.IGRS-050/2026
SubjectDetection and investigation methodology for software supply chain attacks affecting Indian organizations
CategoryThreat Intelligence
AuthorManuj Kumar Pandey
Published2026-05-06
Reading time6 minutes

Supply chain attacks compromise trusted software to reach downstream targets. The SolarWinds and XZ Utils attacks defined a generation of threat. How to detect and investigate them.

Why supply chain attacks are so effective

A supply chain attack compromises trusted software at the source — the build pipeline, the software repository, or the update mechanism — so the malicious modification reaches every downstream user who installs or updates that software. The attack bypasses direct intrusion defences because it enters through a trusted channel: code passing signing checks, from a known vendor, installed by legitimate update mechanisms that security teams have explicitly allowed.

The attack patterns

Compromised build environment: Attacker accesses the build server and injects malicious code into compiled binaries before signing — the source code remains clean, but the binary is malicious. Compromised open-source package: Apparently legitimate code contributed to a widely used package with malicious functionality hidden or conditionally triggered — the XZ Utils backdoor discovered in 2024 is the canonical example. Typosquatting: A malicious package published to npm, PyPI, or similar repositories with a name nearly identical to a legitimate package. Compromised update mechanism: Vendor update server or signing key compromised, allowing malicious updates to reach all users — the SolarWinds Orion attack pattern.

Detection techniques

Software composition analysis (SCA) tools maintain inventories of all third-party dependencies and alert on new versions or known-vulnerable components. Binary integrity verification compares installed software hashes against vendor-published hashes. Behavioural monitoring detects unexpected network connections or file system activity by newly updated software that previously behaved normally.

Incident investigation

When supply chain compromise is suspected, investigation must extend to all systems that installed the same affected version during the relevant window. Map which version was installed when, on which systems. Treat all those systems as potentially compromised until proven otherwise through forensic review. Identify all network connections made by the compromised software — these reveal C2 infrastructure and exfiltration destinations.

For Indian organizations using open-source components, a Software Bill of Materials (SBOM) — a structured inventory of all components, versions, and dependencies — is the foundation for supply chain risk management. Without it, you cannot know what you are running, let alone whether it has been compromised.
