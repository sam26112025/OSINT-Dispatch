Kali365: The Microsoft 365 Phishing Kit That Bypasses MFA — What the FBI Warning Means for India

For more than a decade, the standard advice has been simple: turn on multi-factor authentication and you are safe from most account takeovers. A phishing kit called Kali365 has quietly broken that assumption. On 21 May 2026 the FBI's Internet Crime Complaint Center issued a public service announcement (alert I-052126-PSA) warning that Kali365 is hijacking Microsoft 365 accounts without stealing a single password and without tripping MFA. The technique it abuses is legitimate, the infrastructure it touches is Microsoft's own, and the barrier to entry is a Telegram subscription. This briefing explains what is actually happening, why it defeats the controls most organisations rely on, the forensic traces it leaves, and what Indian organisations and users should do now.

What the FBI actually warned about

The FBI describes Kali365 as a Phishing-as-a-Service (PhaaS) platform — a criminal subscription product, sold and supported much like a legitimate SaaS startup. It was first observed in April 2026 and has been distributed mainly through Telegram. According to the advisory, the platform lowers the barrier of entry for less-technical attackers by bundling AI-generated phishing lures, automated campaign templates, real-time dashboards for tracking targeted individuals and entities, and — the dangerous part — the ability to capture OAuth tokens and gain persistent access to a victim's Microsoft 365 environment. Independent security firms reported hundreds of attacks in April alone, spanning manufacturing, education, government, insurance, financial services and healthcare across North America and Europe. Public reporting has put the subscription price at roughly USD 250 for a month or about USD 2,000 for a year — trivial against the value of a hijacked corporate mailbox.

How the attack works — device code phishing

The core technique is known as device code phishing, and it abuses a genuine Microsoft feature called the OAuth device authorization (device code) flow. That flow was designed to let people sign in on devices that lack a keyboard — smart TVs, conference-room displays, industrial terminals — by showing a short code that the user types into microsoft.com/devicelogin on a phone or laptop. Kali365 turns this convenience into a trap. At a conceptual level the FBI describes four stages:

  1. Lure. The victim receives a phishing email impersonating a trusted cloud or document-sharing service — a file shared on SharePoint or OneDrive, a signature request styled after DocuSign or Adobe Acrobat Sign. The email contains a short code and asks the recipient to visit a Microsoft verification page and enter it.
  2. Authorization. The link genuinely goes to Microsoft's own page. The victim enters the code — and in doing so unknowingly authorises the attacker's device to access their account.
  3. Token theft. The attacker's device receives OAuth access and refresh tokens tied to the victim's account.
  4. Persistence. With those tokens, the attacker reads Outlook mail, Teams chats and OneDrive files — and keeps coming back — without ever needing the password or another MFA prompt.

Reporting indicates Kali365 also offers a second mode, sometimes referred to as "Cookie Link" — an adversary-in-the-middle approach that proxies the victim through attacker-controlled infrastructure to capture the authenticated browser session and cookies after a normal login. Either way, the prize is the same: a live, token-backed session rather than a password.

Why it defeats MFA

This is the uncomfortable insight for every security team. Because the victim signs in on the real Microsoft page and completes their own MFA challenge, Microsoft correctly issues valid tokens — to the attacker's authorised device. There is no fake login page to spot, no suspicious domain in the address bar, and often the victim's own organisational branding is shown. Legacy secure email gateways see only a benign link to microsoft.com. Password managers do not help because no password is phished. Credential-monitoring and breach-alerting do not fire because nothing was breached in the classic sense. The control that "failed" was never bypassed technically — it was satisfied by the genuine user. That is why the FBI's framing matters: MFA remains essential, but it is no longer sufficient on its own.

Once inside, the blast radius extends well beyond email. Because Microsoft 365 is a single sign-on hub for many organisations, a hijacked identity can open the door to SharePoint, OneDrive, Teams and any third-party SaaS — CRM, finance, HR — connected through Microsoft SSO. Kali365 is not the only product in this space; researchers have flagged a parallel Telegram-sold kit called EvilTokens with similar ambitions, which signals a broader shift in the criminal market from password theft to token and session theft.

The single red flag every user must learn

Strip away the sophistication and there is one behaviour that stops this attack cold: never enter a device code that somebody sent you. The microsoft.com/devicelogin page is legitimate, and a code is legitimate only when it appears on a device you are personally signing into that has no keyboard. If an email, chat message, shared document, or QR code asks you to go to that page and type in a code, treat it as an attack regardless of how convincing the branding looks. A device code arriving in your inbox is the digital equivalent of a stranger handing you a key and asking you to install it in your own front door.

Defensive playbook — for organisations

The FBI's advisory and the wider response converge on a small set of high-impact controls. For organisations running Microsoft 365 / Entra ID:

  1. Block the device code flow with Conditional Access. Create a Conditional Access policy that blocks device code flow for all users, with narrow, documented exceptions only for the rare workflows that genuinely need it.
  2. Audit before you block. Review existing device code flow usage first to identify any legitimate dependencies, so the block does not break a real business process.
  3. Restrict authentication transfer from computers to mobile devices, closing a related path attackers use.
  4. Exclude emergency "break-glass" accounts from the block so administrators are not locked out.
  5. Move to phishing-resistant MFA. FIDO2 / hardware security keys and certificate-based authentication tie the login to a physical device and a verified origin, and are far harder to abuse than one-time codes or push approvals.
  6. Harden the token layer. Enable token protection and Continuous Access Evaluation, shorten session lifetimes for sensitive roles, and ensure your team can rapidly revoke refresh tokens and active sessions — because revoking a password does nothing to a stolen token.
  7. Monitor for the tell-tales: device-code sign-ins, new device registrations, anomalous token grants, impossible-travel logins, and the sudden creation of mailbox forwarding or inbox rules.

Defensive playbook — for individuals

  1. Honour the one rule: only ever enter a device code for a sign-in you started yourself, on a device without a keyboard. Codes you receive by email or message are hostile.
  2. Slow down on "urgent" document or signature requests. Urgency is the lever; a pause to verify through a known channel defeats the script.
  3. Prefer passkeys / hardware keys where your account supports them.
  4. Review your account's active sessions and authorised devices periodically, and remove anything you do not recognise.
  5. Check your exposure. If you reuse credentials, confirm whether your email or passwords already appear in known breaches using a privacy-first checker such as the IGRS Breach Check tool, and move to unique passwords plus phishing-resistant MFA.

The investigator's view

Token-theft compromises do not look like password compromises, and treating them the same way is how they go unnoticed. The durable evidence sits in the identity provider, not the endpoint. In a Microsoft 365 investigation, the high-value artefacts are the Entra ID sign-in logs (specifically authentications using the device code flow and the device/app that received the grant), unfamiliar device registrations, refresh-token issuance and reuse, and Unified Audit Log events such as MailItemsAccessed, new inbox or transport rules, and OneDrive/SharePoint file access from unexpected IPs or ASNs. A practical pivot is to take the suspicious source IP from a token grant and profile it — hosting versus residential, ASN, geolocation, and abuse history — before correlating it across accounts; the IGRS IP Lookup tool is built for exactly that triage. The investigative goal is to establish the window of access, scope what the token could reach across SSO-connected applications, and preserve the relevant logs with hash integrity for admissibility — then force a clean cut by revoking tokens and sessions, not merely resetting a password.

The India angle

Microsoft 365 is deeply embedded across Indian enterprises, educational institutions and government bodies, which makes this threat directly relevant here rather than a distant American advisory. Indian organisations carry a specific obligation: under the CERT-In Directions of 2022, qualifying cyber incidents must be reported to CERT-In within six hours of detection, so an identity-takeover incident should trigger that clock alongside internal containment. Where money is moved off the back of a hijacked mailbox — a fake vendor-payment instruction sent from a compromised but genuine internal account is a classic follow-on — victims should call the 1930 cyber-fraud helpline and file on the National Cybercrime Reporting Portal immediately, because speed is what allows mule accounts to be frozen. Affected parties in the United States, and Indian entities with a US nexus, can also report to the FBI's IC3 at ic3.gov as the advisory requests.

Bottom line

Kali365 is not a clever new exploit so much as a clever new business — packaging a known weakness in a legitimate authentication feature into a turnkey, AI-assisted subscription that anyone can rent. The lesson is structural, not tactical: the perimeter has moved from passwords to identities and tokens, and defences must move with it. For organisations that means blocking the device code flow, adopting phishing-resistant MFA, and being able to revoke tokens fast. For users it comes down to one durable habit — never type a code someone sent you. And for investigators, the case is built not in the inbox but in the identity logs, where the stolen token leaves its trail.

Frequently Asked Questions

Does MFA still protect me against Kali365?
MFA is still essential, but device code phishing defeats traditional MFA because the victim completes the challenge themselves on a genuine Microsoft page and the attacker collects the resulting tokens. The durable defences are phishing-resistant MFA (FIDO2 / hardware keys) plus a Conditional Access policy that blocks the device code flow for users who do not need it.
What is the one thing every user must remember?
Never enter a device code that someone sent you. The microsoft.com/devicelogin page is genuine, but you should only type a code there during a sign-in you personally started on a keyboard-less device. A code arriving by email, chat or document is an attack.
How do I tell if an account was hijacked this way?
Review Entra ID sign-in logs for device code flow sign-ins and unfamiliar device registrations, check for new mailbox forwarding or inbox rules, and look for token-grant and MailItemsAccessed events from unexpected IPs. If compromise is suspected, revoke all refresh tokens and sessions, reset credentials, and report to IC3.gov, CERT-In and the 1930 helpline if money is involved.
Is this only an enterprise problem?
No. Early reporting focused on organisations, but the same technique works against any individual with an Outlook, OneDrive, Teams or Microsoft 365 account who can be tricked into entering a device code on the real Microsoft page.
