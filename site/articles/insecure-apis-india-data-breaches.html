Why India's Biggest Data Breaches Start with Insecure APIs

Look closely at the post-mortems of India's largest data exposures and a single thread runs through almost all of them. The headlines name the organisation; the root cause is usually the same plumbing — an Application Programming Interface (API) or endpoint that handed out data it should never have. Analyses of incidents from the Aadhaar exposure to the ICMR leak to a string of consumer-app breaches repeatedly point to APIs that lacked proper authentication, authorisation or rate-limiting. APIs are the connective tissue of modern digital India — and when they are weak, they leak at scale.

Why APIs are the soft underbelly

A web page is built for humans; an API is built for machines, and it returns clean, structured data on request. That is precisely what makes a weak API so dangerous. Where a website might force an attacker to scrape page by page, a poorly secured API can return records in neat JSON, a thousand at a time, to anyone who asks. Add India's sheer scale — population-level identity systems, UPI, hundreds of millions of app users — and a single flawed endpoint becomes a firehose. The breaches that defined the last few years were rarely Hollywood-style intrusions; they were ordinary requests to endpoints that never checked who was asking.

The recurring failure patterns

The same handful of weaknesses show up again and again. They map almost one-to-one onto the OWASP API Security Top 10:

FailureWhat goes wrong
Broken Object Level Authorization (BOLA / IDOR)The API trusts an ID in the request without checking ownership. Change the ID, get someone else's record. The most common and damaging API flaw.
Broken authenticationWeak, missing or guessable tokens; endpoints that never required a login in the first place.
Excessive data exposureThe API returns the full record (including fields the UI never shows) and relies on the client to hide them.
No rate limitingNothing stops an attacker from enumerating IDs or scraping the entire dataset through millions of automated calls.
Security misconfigurationDebug endpoints, default credentials, verbose errors and exposed documentation left in production.

None of these are exotic. They are the cumulative result of shipping fast and bolting security on later — which is exactly what rapid digitisation incentivises.

Why it keeps happening in India specifically

The pressure to digitise public services, finance and commerce at population scale has produced an explosion of APIs, often built and integrated by multiple vendors under tight deadlines. Authentication and per-object authorisation are easy to get wrong and easy to defer. Third-party and vendor integrations — the same supply-chain pathway behind several recent enterprise breaches — widen the surface further: your data is only as safe as the least careful partner holding a key to your API. When the data in question is Aadhaar numbers, PAN, health records or financial details, the blast radius is national.

How to defend (and test responsibly)

Defence starts with knowing what you have. You cannot protect an endpoint you forgot you published, so a complete, continuously updated API inventory is step one. From there:

  • Authorise every object, every time. Check that the authenticated caller owns or may access the specific record — never trust an ID from the client.
  • Authenticate strongly with short-lived tokens, and apply rate limiting and anomaly detection to choke enumeration and scraping.
  • Return only what the use case needs. Filter at the server, not the client; never ship hidden fields and hope the UI conceals them.
  • Test against the OWASP API Security Top 10 — on systems you own or are explicitly authorised to assess — combining automated scanning with manual per-object authorisation checks, and validate that logging and monitoring would actually catch abuse.

For investigators and red teams, the discovery phase overlaps heavily with OSINT — mapping subdomains, documentation and exposed endpoints is the same recon discipline covered in our guide to API security and OSINT recon, always within an authorised scope.

When prevention fails: the legal clock (India)

If a personal-data breach occurs, the Digital Personal Data Protection Act, 2023 requires the data fiduciary to notify the Data Protection Board and affected individuals. In parallel, CERT-In directions require reporting qualifying cyber incidents within six hours of detection, and listed companies face separate disclosure timelines to the exchanges. Building the response runbook before an incident — not during one — is the difference between a contained event and a crisis, a theme we expand on in our India data-breach response guide.

Frequently Asked Questions

Why do so many Indian data breaches trace back to APIs?
India digitised at enormous speed and scale, and many services exposed APIs that lacked proper authentication, authorisation and rate limiting. Because APIs return structured data directly, a single weak endpoint can leak millions of records with simple, repeated requests.
What is broken object level authorization (BOLA / IDOR)?
It is when an API trusts a user-supplied identifier without checking that the caller is allowed to access that specific record. Changing an ID in the request returns someone else's data — the single most common and damaging API flaw.
What does the DPDP Act require after a personal data breach?
The Digital Personal Data Protection Act, 2023 requires data fiduciaries to notify the Data Protection Board and affected individuals. Separately, CERT-In rules require reporting qualifying cyber incidents within six hours of detection.
How can an organisation test its APIs safely?
Only test systems you own or are authorised to assess. Combine a full endpoint inventory, automated and manual checks against the OWASP API Security Top 10, per-object authentication and authorisation testing, and rate-limit and logging validation.
