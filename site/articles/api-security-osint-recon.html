API Security Reconnaissance: How Attackers Map Your APIs Before You Know They Exist

File No.IGRS-035/2026
SubjectOSINT techniques for API discovery and security assessment in authorized environments
CategoryThreat Intelligence
AuthorManuj Kumar Pandey
Published2026-06-03
Reading time6 minutes

Most organizations do not have complete inventories of their own APIs. Attackers find what defenders miss. The discovery techniques and how to get ahead of them.

The API sprawl problem

Modern applications are built from APIs — internal services, partner integrations, mobile backends, and third-party connections that collectively represent an organization's most sensitive data pathways. The security problem is that most organizations do not have accurate, complete inventories of their own APIs. APIs are created by development teams without security review, exposed in mobile apps, published to developer portals, and sometimes forgotten when the product they served is deprecated. Attackers — and security researchers doing authorized assessments — use OSINT techniques to discover this undocumented API surface before defenders know it exists.

JavaScript file analysis

Modern web applications load JavaScript bundles that contain API endpoint references — the paths, parameters, and sometimes authentication patterns for every API call the frontend makes. These bundles are publicly accessible to any user of the application. Tools like LinkFinder and JSParser extract API endpoints from JavaScript files automatically. The process: load the target application, identify all JS files from the network tab of browser developer tools, pass each through the analysis tool, and review the extracted paths for undocumented or sensitive endpoints. This regularly surfaces internal API paths that developers assumed were not publicly discoverable.

Mobile application analysis

Mobile apps are another rich source of API endpoint discovery. Android APKs and iOS IPAs can be decompiled to reveal hardcoded API endpoints, authentication tokens (a frequent security failure), environment-specific endpoints (staging, development, production), and sometimes internal documentation comments that reveal system architecture. Tools: jadx for Android APK decompilation, frida for dynamic analysis. For basic endpoint extraction without full decompilation, strings extraction from the binary often reveals URL patterns.

Public sources

Before touching the application, check public sources for API documentation: the organization's developer portal (developer.company.com is a common subdomain); Postman's public API network, where organizations sometimes publish internal API collections; GitHub repositories where employees may have committed code containing API endpoint references or, in serious cases, API keys; and Wayback Machine snapshots of developer portals or API documentation that may have been removed.

This reconnaissance methodology is appropriate for authorized security assessments of your own organization's APIs or in scope systems during a penetration test. Applying it to systems you do not have authorization to test constitutes unauthorized access under Section 66 of the IT Act.

Shodan for API discovery

Shodan indexes internet-facing services including API servers. Queries combining organization name, known IP ranges, and port patterns can surface API servers that are not linked from the organization's public website. Non-standard ports (8080, 8443, 3000, 5000) are particularly worth checking — development and staging APIs often run on these ports and may be exposed to the internet without the security controls applied to production systems.

Frequently Asked Questions

How do attackers find exposed APIs through OSINT?
Attackers discover APIs through Google dorking, GitHub code searches for API keys, Shodan/Censys scans, mobile app reverse engineering, JavaScript file analysis, and API documentation discovery. Exposed endpoints and leaked keys are common findings.
What are common API security vulnerabilities?
Common API flaws include broken object level authorization (BOLA), broken authentication, excessive data exposure, lack of rate limiting, mass assignment, and improper inventory management — as documented in the OWASP API Security Top 10.
How can you protect APIs from OSINT-based attacks?
Protect APIs by removing keys from client-side code, rotating exposed credentials, implementing rate limiting, using API gateways, enforcing strong authentication, monitoring for leaked keys on GitHub, and maintaining an accurate API inventory.
